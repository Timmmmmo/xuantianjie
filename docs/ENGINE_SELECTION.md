# 游戏引擎选型评估（性能 / 小游戏场景）

> 背景：当前为 **纯 Canvas2D + 原生 JS**（零依赖）。担心「数据量大时卡顿」是否不适合小游戏。  
> 结论：**不必为性能立刻换引擎**；卡顿主因通常是热路径分配与滥用特效，而非 Canvas 本身不够用。

## 1. 现状

- 同屏妖潮 + 弹幕 + 粒子；已有 `RENDER_CAP` / `Quality` 三档  
- 风险：每帧渐变、无上限粒子、全屏 `shadowBlur`、O(n²) 逻辑  
- 优势：包体极小、可离线 PWA、渠道友好  

Canvas2D 在 100–200 精灵级幸存者可 60fps（中端机 + 降档）。

## 2. 对比

| 方案 | 优势 | 代价 | 对本项目 |
|------|------|------|----------|
| Canvas2D（现用） | 零依赖、最小包体、已上线 | 自建绘制工具 | **保持** |
| PixiJS | WebGL 批处理精灵更稳 | +体积、破坏零依赖 | 二期渲染层候选 |
| Phaser 3 | 全套游戏件 | 重、黑盒 | 不推荐主包 |
| Cocos / Laya | 小游戏平台/广告 SDK 成熟 | 重写、工作流绑定 | 重度渠道运营再评 |
| Unity WebGL | 3D | 包体/加载差 | 不适合 |
| Three.js | 3D | 非 2.5D 割草所需 | 仅独立 demo |

## 3. 建议

1. **现在**：优化 Canvas（少分配、粒子预算、关阴影、DPR 上限），用真机 FPS 决策。  
2. **仍卡**：只把绘制层换成 Pixi，逻辑/存档不动。  
3. **要上快应用/微信重度运营**：再评 Cocos/Laya。  

**必须换引擎的门槛**：500+ 动画精灵 60fps、骨骼编辑流水线、复杂物理/3D、多人同步 —— 当前 MVP 不满足。

## 4. 本包稳定性（配合性能）

- **`draw()` / `salvageFrame` 异常时均不再 `clearRect` 整屏**（避免角色闪没）  
- 单只 `drawEnemy` 失败不影响整帧  
- `roundRect` 兜底、血条 NaN 防护、贴图 `drawImage` 校验  

**结论**：保持 Canvas2D；先吃优化甜点；数据不达标再上 Pixi，而不是全面换 Phaser/Cocos/Unity。
